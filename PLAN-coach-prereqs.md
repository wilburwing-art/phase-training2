# Phase 8 — AI Coach Prerequisites

Successor to PLAN-routines.md. Lays the structured plan + memory + feedback + planner substrate the AI coach needs to *act* on, before any chat UI ships. Each phase is a TestFlight-worthy increment — additive, no regressions to the existing Start → Log → Complete → History flow.

## Problem

The coach must propose and apply plan changes, explain *why* the plan changed, and remember preferences. None of that is possible against today's data model:

- The "plan" is one hardcoded `upper-1` template + an ad-hoc routine picker.
- There is no week. There is no notion of *today's day* in a plan.
- There is no onboarding, no preference store, no soreness log, no structured feedback signal.
- There is no plan-edit pipeline — nothing the coach (or a long-press gesture) can call to mutate the week.
- There is no planning engine — nothing assembles a sensible first week from user inputs.
- Navigation is a linear `Route` enum, not a tab shell. "Across-screen Ask Coach" has no surface.

## Definition of done

After Phase 12 lands, the coach (chat layer, Phase 13, out of scope here) has:

1. A persisted `WeekPlan` generated by a deterministic rules engine from onboarding inputs.
2. A `PlanDiff` → preview → apply pipeline it can call.
3. A `TrainingMemory` store it can read and append to.
4. Structured soreness + pre-workout + post-workout + weekly-check-in feedback flowing into memory.
5. Five tabs (Today / Week / Train / Progress / Profile) so "Ask Coach" can be screen-aware.
6. A weekly check-in loop that regenerates next week's plan from updated intent + feedback.

No coach-specific (LLM) code ships in Phases 8–12. The chat layer slots on top.

## Out of scope

- The chat UI itself (drawer, bubbles, prompt chips, plan-preview cards). Phase 13.
- LLM wiring, API keys, prompt design, function-calling schemas. Phase 13.
- Cycle-aware personalization screen + notification preferences screen. Deferred to a later polish phase.
- Multi-week periodization, mesocycle planning. Single week is the unit.
- HealthKit / Strava / Whoop / Garmin integrations. Manual inputs only.
- Onboarding paywall, accounts, sync, cloud sync.

## Locked decisions

| Decision | Value | Rationale |
|---|---|---|
| Nav shell | `TabView` with 5 tabs (Today / Week / Train / Progress / Profile) | Coach is "across screens" — needs tabs to be across. |
| Existing 4-screen flow | Lives inside Today tab (workout flow) + Train tab (existing routine library) | Routines/Picker/ExerciseDetail screens move to Train tab; Today owns the active workout. |
| WeekPlan storage | `UserDefaults` + `Codable`, single key `pt_week_plan` | Consistent with existing persistence. SQLite migration deferred. |
| WeekPlan shape | `[DayPlan]` indexed by `Date` (start-of-day), rolling 7 days from today | Coach edits this week + next week only. |
| DayPlan kinds | `enum DayKind: lift / sport / mobility / rest / event` | Sport covers climb/ski/run; event is a "protected" day. |
| Planning engine | **Rules-driven over `coach.db`**, deterministic, no LLM | Predictable. No API cost per plan. LLM only edits the engine's output (Phase 13). |
| First-plan generation | At end of onboarding (Phase 9) → previewed → accepted | Plan exists from day one; user never sees an empty Week tab. |
| Routine ↔ DayPlan | `DayPlan.lift` references a `coach.db` routine by id; `DayPlan.mobility` likewise | Train tab is the same corpus the planner pulls from. |
| PlanDiff | Returned by every plan-edit op; UI renders before/after card; user Apply/Reject commits | Same seam coach uses in Phase 13. |
| TrainingMemory | Typed Codable struct, single key `pt_training_memory`, versioned schema | Sports, season, equipment, schedule, dislikes, constraints, feedback, soreness, check-ins. |
| Soreness/state | Pre-workout chip row on Today: energy / soreness / pain / time / equipment | Captures everything the rules engine + future coach need to adapt today's session. |
| Post-workout feedback | Extends CompleteScreen — chips: "too easy" / "right" / "too hard" / "[exercise] hurt" / "ran long" | Structured rows into `TrainingMemory.feedback`. |
| Weekly check-in | Triggered weekly; captures next-week intent + previous-week feedback; re-runs planner | The real retention loop. Ships before the coach. |
| AI Insight Card | Reusable component used on Today / Week / Post-workout | Static copy in Phase 11; coach-fed in Phase 13. |
| Onboarding scope | 8 screens (welcome, sports, focus, season, availability, equipment, experience, constraints) | Cycle-aware + notification-setup deferred to a polish phase. |
| Cold launch with no onboarding | Forced into onboarding flow on first run | Plan only exists after onboarding. |

### Phase 10 — WeekPlan model + rules-based planner + Week tab (read-only)

**Goal:** Deterministic rules engine generates a 7-day plan from `TrainingMemory`. Plan persists. Week tab renders it. Today tab reads today's `DayPlan` instead of hardcoded `upper-1`.

**New files:**
- `PhaseTraining/Data/WeekPlan.swift`:
  ```swift
  enum DayKind: String, Codable { case lift, sport, mobility, rest, event }
  struct DayPlan: Codable, Identifiable {
      var id: UUID
      var date: Date
      var kind: DayKind
      var title: String
      var routineId: Int?         // coach.db routine id when kind == .lift / .mobility
      var sport: Sport?
      var protected: Bool
      var notes: String?
      var generatedReason: String? // human-readable rule trace
  }
  struct WeekPlan: Codable {
      var days: [DayPlan]          // exactly 7, rolling from today
      var generatedAt: Date
      var inputsHash: String       // detect when memory has drifted
  }
  ```
- `PhaseTraining/Data/PlanStore.swift` — `@Published var plan: WeekPlan?`. Calls `Planner.generate(memory:)` at end of onboarding and on weekly check-in.
- `PhaseTraining/Data/Planner.swift` — pure function `Planner.generate(memory: TrainingMemory, routines: [Routine]) -> WeekPlan`:
  1. Look up `WeeklyShape` for `(primarySport, season)`.
  2. Place fixed sport days first.
  3. Place lift/mobility/rest around them with spacing rules (e.g., no legs day immediately before climb).
  4. For each `.lift` / `.mobility` slot, pick a `coach.db` routine matching goal + equipment + duration.
  5. Stamp each day with `generatedReason`.
- `PhaseTraining/Data/WeeklyShape.swift` — lookup tables. Per `(primarySport × season)` → ordered list of `DayKind` with priority. ~15 combinations to start.
- `PhaseTraining/Screens/WeekScreen.swift` — vertical list of 7 days. Each row: dow, date, kind badge, title, protected lock if set. Today row highlighted. No editing yet.
- `PhaseTrainingTests/PlannerTests.swift` — deterministic outputs for fixed inputs (in-season climber / pre-season skier / off-season strength / equipment-restricted).

**Modified:**
- `PhaseTraining/Screens/StartScreen.swift` → renamed `TodayScreen.swift`. Hero pulls from `planStore.plan.today`. Rest-day card if today is `.rest`. Sport-day card if `.sport` (no exercise list, just "log when done"). Lift-day uses today's routine.
- `PhaseTraining/Screens/Onboarding/OnboardingFlow.swift` — last step calls `Planner.generate` + shows preview screen → "Accept plan" → land on Today.
- `PhaseTraining/App/RootTabView.swift` — wire Week tab.

**Acceptance:** Onboarding ends on a plan preview. Accept → Week tab shows 7 days, Today matches today's row. Re-run onboarding with different inputs (in-season climber vs off-season strength) → meaningfully different plans. Planner tests green.

### Phase 11 — Pre-workout check-in + PlanDiff + manual editing

**Goal:** Pre-workout check-in on Today captures energy/soreness/pain/time/equipment-change. Plan can be edited *by hand* — long-press to move, swap, protect, shorten, remove. Every mutation goes through `PlanStore.propose(_:) -> PlanDiff` → preview → `apply()`.

**New files:**
- `PhaseTraining/Data/PlanEdit.swift`:
  ```swift
  enum PlanEdit {
      case move(dayId: UUID, toDate: Date)
      case swapKind(dayId: UUID, to: DayKind, title: String, routineId: Int?)
      case protectDay(dayId: UUID, eventTitle: String)
      case shorten(dayId: UUID, toMinutes: Int)
      case addSession(date: Date, kind: DayKind, title: String, routineId: Int?)
      case removeSession(dayId: UUID)
  }
  struct PlanDiff {
      let before: WeekPlan
      let after: WeekPlan
      let edits: [PlanEdit]
      let reasoning: String?       // coach-supplied in Phase 13
  }
  ```
- `PhaseTraining/Components/PlanDiffSheet.swift` — bottom-sheet preview. Before/after stacked. Apply / Cancel.
- `PhaseTraining/Components/PreWorkoutCheckIn.swift` — chip row on Today: energy (low/normal/high), soreness (none/mild/high + body areas), pain (yes/no), time (planned/less/more), equipment (same/different). Writes `SorenessEntry` to memory.
- `PhaseTraining/Components/InsightCard.swift` — reusable. Slot for "Because X → I changed Y → so that Z". Static copy this phase.

**Modified:**
- `PhaseTraining/Data/PlanStore.swift` — adds `propose(_:) -> PlanDiff` and `apply(_:)`. Apply is the only public mutation point.
- `PhaseTraining/Screens/WeekScreen.swift` — long-press a day → action menu (Move / Change kind / Protect / Shorten / Remove). Each builds a `PlanEdit`, calls `propose`, presents `PlanDiffSheet`.
- `PhaseTraining/Screens/TodayScreen.swift` — chip row above exercise list, collapsed by default. Reserved Insight Card slot above hero.

**Acceptance:** Pre-workout chips persist with today's date. Long-press Thursday's lift → "Move to Friday" → before/after → Apply → week updates → kill app → reopen → change persists. Cancel discards.

## Risks

| Risk | Mitigation |
|---|---|
| `Route` → `TabView` migration breaks active-session resume | Phase 8 keeps existing routing inside Today tab; resume logic untouched. |
| Onboarding 8 screens feels long | Each screen is one decision; progress bar; "Back" preserves state. Cycle-aware + notification screens already deferred to keep this at 8. |
| Rules engine outputs nonsense weeks for unusual input combos | `WeeklyShape` lookup has a default fallback (3-day full-body + 4 rest). Tests cover the common 8–10 combos. Coach (Phase 13) can edit any bad output. |
| `coach.db` doesn't have routines matching every `(goal × equipment × duration)` slot | Planner relaxes constraints in order: duration → equipment → goal. Always returns a routine; worst case it's a suboptimal match flagged in `generatedReason`. |
| `TrainingMemory` schema churns once coach starts using it | `schemaVersion: Int` on the struct; migration on decode. |
| Phase 11 long-press conflicts with row tap | Tap = view day detail; long-press = action menu. Test on device, not simulator. |
| Weekly check-in feels redundant with daily editing | Daily editing = "today changed". Weekly check-in = "next week's intent + last week's feedback". Different cadences, different inputs. |
| Planner regression on every `coach.db` rebuild | `PlannerTests` golden outputs catch routine-id drift. |

## After Phase 12

Phase 13 is the coach itself: Anthropic API client, system prompt that reads `TrainingMemory` + `WeekPlan`, function-calling for `PlanEdit` cases, "Ask Coach" drawer button on Today / Week / Active workout / Complete / Progress, prompt chips, plan-diff preview card inline in chat. The coach **edits and explains** — it does not generate the week (the rules engine does). Out of scope here.
