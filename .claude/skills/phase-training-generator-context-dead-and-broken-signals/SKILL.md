# GeneratorContext dead & broken signals (audited, phase-training2)

Method note: these were found by grepping for actual READS and tracing logic, not by reading doc comments. The doc comments in GeneratorContext.swift describe INTENDED behavior that in several cases was never wired. Always verify a signal is consumed before trusting its comment.

## Status (2026-05-31)
Findings **1, 2, 4, 5 are FIXED** this session (verified: WorkoutGeneratorTests + GeneratorContext/Readiness suites, 44 tests green). Only **#3 (drift hash) and the degraded-by-default note remain open.** Don't re-flag the fixed ones — if you're editing nearby, just confirm the fix still stands. Full record: `phase-training2/docs/generator-audit.md`.

## Confirmed
1. **[FIXED — deleted] muscleVolume was dead.** Was computed (4-week MuscleVolume.rows walk) every regen, never read. Deleted the field + `buildMuscleVolume` builder from GeneratorContext.swift (the `MuscleVolume` utility stays — it powers ProgressScreen + CoachContext). Two test constructors updated. If it reappears, it's still dead unless an accessory-pick reader was added.

2. **[FIXED — bridged] Sore EXCLUSION filter missed the big compounds.** Soreness areas are `MuscleBucket` rawValues: chest, back, shoulders, biceps, triceps, forearms, quads, hamstrings, glutes, calves, core (ExerciseFilters.swift:18). applySoreFilter (WG:338) maps the exercise's primary muscles to `.label.lowercased()` and matches `label.contains(area)||area.contains(label)`. Verified against coach.db labels: **MISSES quads (vs "Quadriceps"), shoulders (vs "Anterior Deltoid"), back (vs "Latissimus Dorsi"), calves (vs "Gastrocnemius"/"Soleus"), core (vs "Rectus Abdominis")**; works only for chest/glutes/hamstrings/biceps/triceps. The correct bridge `MuscleBucket.bucket(forSlug:)?.rawValue` + `memberSlugs` EXISTS (ExerciseFilters.swift:44,97) and the RPE-7 cap path `isMuscleSoreForExercise` (WG:868) uses it correctly — only the exclusion filter bypasses it. **Done:** applySoreFilter now maps each primary slug through `MuscleBucket.bucket(forSlug:)?.rawValue` and excludes if any bucket ∈ recentSoreAreas. Test: `test_soreFilter_excludesQuadPrimaryExercisesWhenQuadsSore` (control proves a legs day normally has quad-primary work).

3. **Drift hash ignores adaptive inputs.** planInputsHash = profile/intent only. Drift detector `plan.inputsHash != memory.planInputsHash` (PlanStore.swift:852) → banner never fires when context changes the plan. Determinism holds only for fixed (hash, context, recentlyPicked, strategy).

4. **[FIXED — Option A "sport = fatigue"] Sport days were double-signed.** recentHardSportDays → applyRecentSignalBias trims a lift day (fatigue); the SAME sportLogs also fed buildReadinessEvents → higher readiness → LESS volume cut. Resolved by excluding hard sport from readiness: `buildReadinessEvents` now filters `log.intensity != .hard`, so a hard sport week trims a day without inflating readiness (light/moderate sport still counts as activity). The planner trim is untouched (it recomputes hard-days locally).

5. **[FIXED — round to 2.5 lb] Progression no-op ≤100 lb.** Was `max(w, (w*1.025/5).rounded()*5)` (WG:591): for any w≤100, 2.5% < 2.5 lb so round-to-5 returned w → +0 lb (20→20, 95→95). Extracted to internal `steppedTargetLb` and changed the grid to 2.5 lb, so mid loads progress (65→67.5, 95→97.5, 225→230); loads <~50 lb still no-op by design (no micro-loading). `formatTargetHint` updated to show the half-pound. Test: `test_steppedTargetLb_progressesMidLoadsNotMicroLoads`. Rep-mismatch sub-bug also FIXED: the note now shows load only ("target: 230 lb", no rep count — it's a load to work up to at the row's prescribed reps; `formatTargetHint` dropped its `reps` param, override test updated to "target: 175 lb"). **Rep-range-blind load ALSO FIXED:** `priorBest` is the heaviest set at ANY rep count, so a 225×3 top set was the target for a 6-12 set (too heavy). `progressiveOverloadHint` now takes `prescribedReps` and routes through `progressiveTargetLb(priorWeight:priorReps:prescribedReps:)`: e1RM via `StrengthStandards.epley1RM` → inverse-Epley load for the band midpoint (`repBandMidpoint`) → 2.5% step. So 225×3→6-12 = 195 lb; 100×10→5 = 117.5 lb (heavier for fewer reps); AMRAP/"30s hold" → nil → falls back to raw stepped weight. Tests: `test_progressiveTargetLb_mapsPriorBestToPrescribedReps`, `test_repBandMidpoint_parsesBands`. All generator findings except #3 (drift hash) are now closed.

6. **`patternFrequency` reorder is a no-op (found 2026-06-04 via the sweep report).** `reorderByPatternFrequency` (WG:~514) sorts `slot.alternatives` ascending by training count so under-trained patterns are TRIED first — but the final pick is unchanged: the staple pre-pass + `deterministicPick` land on the same exercise regardless of alternative order. Proof it's not a probe artifact: in `GeneratorSweepReportTest`, seeding `patternFrequency` with control patterns at 10× = DEAD (zero output delta), while `strategy.deprioritizePatterns` fed the SAME pattern set = live. So **removing** a pattern moves output; **reordering** by frequency does not. Distinct from the degraded-by-default note (that's empty context; this is dead even WITH populated data). Root cause (confirmed 2026-06-04): the focus recipes are almost all SINGLE-alternative slots (`["squat"]`, `["horizontal-push"]`…) so the reorder has nothing to reorder; the 2 multi-alt slots are `optional` tails the budget drops. **RESOLVED 2026-06-04: deleted** the field + `buildPatternFrequency` + `reorderByPatternFrequency` (same playbook as #1). The LIVE `CoachContext.patternFrequencySection` (LLM-prompt pattern coverage, reads sessions directly — NOT this field) is untouched. Tests: WorkoutGeneratorTests unchanged-output proves the reorder was inert.

7. **`emphasizePatterns` is inert TOO — but DELIBERATELY RETAINED, do NOT delete (confirmed 2026-06-05).** `strategy.emphasizePatterns` (WorkoutGenerator.swift:580-585) stable-partitions `slot.alternatives` (emphasized first) — same inert-reorder class as #6, because slots are single-alternative. Tempting to delete it the same way. DON'T: `GeneratorStrategy.swift:38-42` explicitly documents the retention ("reordering changes nothing… Retained as part of the LLM build_workout tool surface… Revisit when recipes gain multi-alternative slots"), and its sibling `deprioritizePatterns` (which REMOVES patterns) is live. Removing emphasizePatterns means editing the LLM tool schema (CoachTools.swift:178/325/399), CoachRequestScreen.swift:385, and GeneratorStrategyTests/GeneratorSweepReportTest — i.e. overriding a documented keep-for-future decision. That's a product call, not dead-code cleanup. Contrast with #6 (patternFrequency = internal-only signal, no external contract → deleted cleanly). Rule: an inert field that's on the LLM tool surface + documented as retained is NOT auto-removable; flag it, don't delete.

> Method that caught 1+5: reimplement the pure formula in a standalone `swift file.swift` harness and print computed values across representative inputs. Gotcha on Xcode 26 / Swift 6.3: `String(format:)` with `%` **crashes** the interpreter — use plain string interpolation instead. Full grounded audit: `phase-training2/docs/generator-audit.md`.

## Degraded-by-default warning
Fresh user (no logged sessions, no HK grant) → context = .empty, hasReadinessData = false. The ENTIRE Phase 2/3 layer (readiness, progressive overload, stagnation, pattern frequency, sore filter) no-ops to the Phase 1 demographic generator. "Looks sophisticated, runs degraded by default." Test the populated-context path explicitly.

## Context can be .empty because a CALL SITE dropped it (not just fresh users)
`Planner.generate(... context: GeneratorContext = .empty ...)` defaults the param, so a call site that forgets to thread context silently runs the degraded path even for a data-rich user. **Found 2026-06-05:** `WeeklyCheckInFlow.regenerateAndAdvance` called `Planner.generate` with no `context:`, so `applyReadinessLiftDayFloor` (caps lift days at 3/wk when `readinessScore < 0.3`) never fired during weekly check-in — the one flow where the user just told you they're cooked. `PlanStore.generate` threads it correctly via the **private** `buildGeneratorContext`; flows that build a CANDIDATE plan against local overrides (check-in) can't reach it. **Fix:** added public seam `PlanStore.makeGeneratorContext(memory:today:)` and passed it. When editing or adding any `Planner.generate` call site, grep all of them (`grep -rn "Planner.generate"`) and confirm each threads context — the default makes the omission invisible. Fixed on branch `fix/checkin-readiness-context-and-event-kind`; relevant gate: `ReadinessGeneratorShipGateTests`, `PlannerTests`.
